# Runtime observations

Runtime records are separate from static analysis facts and remain scoped to a snapshot, runtime environment, and run. M12 models `RuntimeEnvironment`, `RuntimeRun`, `TestDefinition`, `TestInvocation`, `RuntimeFunctionEntry`, and `RuntimeCallObservation` independently from `AnalysisEnvironment`.

`identify_pytest_items` accepts pytest item node IDs and creates one `TestDefinition` per unparameterized test plus a distinct `TestInvocation` for each collected case. IDs include the repository-relative file path, so duplicate test module basenames stay distinct. The helper rejects absolute paths, parent traversal, invalid source suffixes, and duplicate node IDs. It does not execute repository code or attempt to discover fixtures itself; only actual collected pytest item IDs should be supplied.

`FunctionEntryTracer` records profiler `call` events only after mapping them to an indexed `Function` or `Method`. A module import event does not count as function execution. Events without a unique static mapping become deduplicated `UNMAPPED_RUNTIME_FUNCTION` diagnostics. The tracer scopes calls to a `TestInvocation` and passes that context to threads created while the invocation is active.

Collection also runs in a container and can execute repository import hooks. Mapped calls observed during collection are stored with `COLLECTION_OR_SESSION` context and are not credited to test invocations.

## Isolated collection and execution

Pytest collection and approved test execution use a new Docker container for each operation. The repository test code, `conftest.py`, and collection hooks run only inside that container. The command is generated by fixed backend code; clients provide collected invocation IDs, never command text.

The container uses an immutable image configured with `RUNTIME_CONTAINER_IMAGE` as a local image ID (`sha256:...`) or a registry digest (`name@sha256:...`). The repository's runtime-test Dockerfile pins Python 3.11.13 slim Bookworm to the linux/amd64 manifest digest and pins pytest. The image must already contain pytest and the repository's approved test dependencies. CodeGraph never installs repository dependencies as part of collection or execution. If Docker, its daemon, or the configured image is unavailable, runtime operations return a clear unavailable response. Static repository inspection continues to work.

Each approved run is bound to a READY graph snapshot, a runtime environment, the collected test invocation IDs, the deterministic pytest argv and its hash, the immutable runtime image, and the execution profile including the pytest plugin and supervisor source hashes. The backend returns the exact argv and hash for review before approval. The UI keeps preparation and approval as separate actions, supports revoking a pending or approved action, and permits execution once. The approval expires after ten minutes. A request body cannot supply shell text, and test selection is limited to collected invocation IDs.

Runtime materialization is separate from analysis input. Analysis still parses the Python/configuration inputs selected by static ingestion. Runtime materialization captures the complete Git-tracked working-tree contents belonging to that ingestion, including dirty and staged changes. Nonignored untracked files are included only when the existing `include_untracked` option is enabled. Ignored files and `.git` internals are excluded. Safe in-repository file symlinks are copied as regular files; external or directory symlinks are omitted under the repository path policy, and external source symlinks retain the static `PATH_REJECTED` diagnostic. Runtime files are stored under a separate content-addressed materialization ID that includes each file's executable status; verification checks file content, size, executable status, path containment, and symlinks before collection and again immediately before Docker launch. Runtime files do not create graph entities. The graph snapshot ID algorithm remains unchanged; the runtime environment ID also binds the materialization ID and pinned image digest.

The container has no network, a read-only root filesystem, a read-only runtime snapshot mount, a bounded writable `/tmp`, dropped capabilities, no-new-privileges, a process limit, CPU/memory limits, a hard timeout, and bounded captured output. It receives only a fixed environment. The container is killed and removed after success, failure, timeout, or cancellation. Runtime containers carry an owner instance ID, backend PID, and process-start marker. Startup reaps a container only when the owner process is demonstrably gone or its PID has been reused; live and uncertain owners, including legacy containers without ownership labels, are preserved. Runtime approvals and active runs are in memory for the single-backend V1 deployment; backend restart invalidates pending approvals. Approval consumption is atomic under an in-process lock, so concurrent requests handled by that process can execute an approval at most once. This guarantee does not coordinate independent backend processes or workers.

Runtime observations remain evidence scoped to a snapshot, runtime environment, and run. Successful, failing, timed-out, or cancelled executions persist their structured terminal result. Instrumentation observations are persisted when the isolated supervisor returns them; a timeout or cancellation may end before it returns any. A failed test's returned partial output remains attached to the run result. These records describe what the instrumentation observed during that execution; they do not claim to cover every possible execution. An unobserved branch or call is not disproven. Runtime observations do not replace static graph facts or create deterministic structural relationships such as `CALLS`, `BINDS_TO`, `IMPORTS`, `OVERRIDES`, or `MAY_DISPATCH_TO`. After an execution result is returned, an already-open investigation is rerun against the same immutable snapshot so persisted run evidence can be shown with its run/environment provenance.

V1 assumes repositories are ordinary, non-adversarial OSS inputs with respect to runtime instrumentation. The in-process pytest plugin reports observations through the container-side supervisor. Isolation protects the host and bounds execution, but V1 does not defend the authenticity of those plugin observations against repository code deliberately written to tamper with the instrumentation. The supervisor keeps child stdout separate from its own result protocol, but this is protocol separation, not cryptographic authentication. Runtime records should therefore be interpreted as instrumentation observations for the named run, not as authenticated structural facts. Adversarially trustworthy external tracing is post-V1 hardening work.

## Static/runtime validation

After an execution, mapped runtime calls are compared with the static candidate set for their uniquely mapped call site. An observed target outside a known static candidate set produces a `RUNTIME_MISMATCH` diagnostic and a run validation report. An unobserved candidate remains unobserved; it is not treated as disproven. Calls at a static site without known candidates can attach as runtime evidence while the report leaves the site unresolved. Calls without a defensible site/source/target join produce `UNMAPPED_RUNTIME_CALLSITE` diagnostics.

The report aggregates repeated observations by call site, source, and target and records invocation IDs and counts. The original per-call observations remain persisted individually. A mismatch updates the corresponding provenance review state for inspection, while leaving the static binding and dispatch candidate facts unchanged. `GET /api/runtime/runs/{run_id}/validation` returns the report for a completed run while its run result is available to the backend process.
